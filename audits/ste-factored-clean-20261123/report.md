## Per-recording factorization implemented, not automatic certification

tools/factored-native-clean.cjs consumes independent SHA-bound suffix and
prefix evidence. It does not contain song IDs, enumerate a catalog product,
install an index or claim a pair is playable. A proposal still needs original
pair rendering/exposure and both-platform actual-player validation.

Source Gilgamesh's published eight native suffix receipts and Sono Ok's
published prefix/exposure are imported without re-decoding or re-rendering
the positive. Per-channel quiet RMS is conservatively bounded by sqrt(2)
times the measured stereo RMS. This is an upper bound, not a new measurement.
Intervals must be fully covered; old eight-second negative cannot borrow a
quiet suffix measured later. The old energetic short tail stays rejected.

Four NEW short prefix decodes only: Djo and Grignani at 44.1/48 kHz, original
stereo from zero, maximum 3.5 seconds, no models or new searches. Djo fails
the frozen .96 overlap peak margin (.98959 original prefix); it is rejected
before native analysis/rendering. Its original .5-second RMS change around
the considered EOF also exceeds 16 dB, but that is composition dynamics,
not proof of a mix-induced volume discontinuity. Do not confuse them.

Grignani prefix passes initial checks: peak .600595/.608135, meaningful
2.25 seconds, original-window level change about +.446 dB. New independent
native prefix receipts are still required; no new usable pair is claimed.
The initial Windows Chromium prefix measurements are saved separately.

The published 6.740 descriptor requires target decoded/media offsets zero.
Both new originals carry declared encoder priming. That can expose a mode
limitation on native backends retaining the raw clock. A recognized raw

tool distinguishes both container-declared durations. No production
validator is relaxed, and no iPhone restriction is removed.

## Separate iPhone diagnostic, never product enablement

The existing iPhone path ALREADY has a confident-tail direct-handoff rule.
Repeating a normal silence skip would not be a new mix and is not counted.
The new isolated prototype studies two native elements primed under a
trusted gesture, retaining source EOF and incoming element identity. Both
audible and muted bootstrap variants are tested, with play() failures
observed. No Web Audio decoding/model runs on the diagnostic phone page.
The app's mixAdoptHandoff iOS refusal remains byte-for-byte unchanged.

The diagnostic needs TWO deliberate gestures and can emit a 100ms bootstrap
fragment. It is therefore not a product-ready UX. It has no application
queue/lyrics/session integration. A successful desktop engine with an iPhone
user agent is ONLY a controlled desktop result, never an iPhone certificate.
Physical device/PWA/background, media-session behavior and audibility remain
mandatory before any iPhone deployment.

Windows Chromium currently passes two controlled natural-EOF prototype
trials (audible/muted bootstrap). These are not added to available-pair
counts. Linux/macOS Chromium/WebKit are requested separately by the manual
factored_native_study workflow, never on ordinary pushes.

## Documentation bounds

[WebKit's autoplay guidance](https://webkit.org/blog/7734/auto-play-policy-changes-for-macos/)
describes per-element grants and checking rejected play promises on macOS.
It does not prove iPhone behavior. The
[archived iOS considerations](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/Using_HTML5_Audio_Video/Device-SpecificConsiderations/Device-SpecificConsiderations.html)
are dated December 2012 and even discuss historical unsupported playbackRate.
Their single-stream statement must not be asserted as a verified rule for
current iOS. This is why measured hardware evidence is required rather than
either assuming two elements will work or declaring them impossible.
